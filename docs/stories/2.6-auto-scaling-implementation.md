## 🎯 **Objective**

Implement auto-scaling infrastructure that can handle **10,000 concurrent users** by automatically adjusting service replicas based on load.

### **Capacity Requirements (YOUR TEST SCENARIO)**

```
Test Parameters:
  - 1,000 Virtual Users (VUs) in k6
  - 10,000 test accounts available
  - Think time: 1 second between requests

Load Calculation:
  RPS = VUs / Think Time
      = 1,000 VUs / 1 second
      = 1,000 requests/second

Current System Capacity (Story 2.2 Baseline):
  - 50 VUs @ 43.55 RPS with 1.5s think time
  - Response time: p95 = 82.67ms (0.083s)
  
  Max Capacity per VU (if saturated):
    Max RPS/VU = 1 / Response Time
               = 1 / 0.083s
               = 12 requests/second per VU
  
  Current System Max Capacity:
    50 VUs × 12 req/s = 600 RPS (theoretical max)
    
  Actual observed: 43.55 RPS (with 1.5s think time)

Required Scaling for 1,000 RPS:
  Current capacity: 600 RPS max
  Required: 1,000 RPS
  Scale Factor: 1,000 / 600 = 1.67x
  
  Replicas Needed:
    Current: 6 replicas (2 per service)
    Required: 6 × 1.67 = 10 replicas total
    
  Distribution:
    - user-service: 2 → 4 replicas (33% of traffic)
    - trip-service: 2 → 4 replicas (40% of traffic)
    - driver-service: 2 → 2 replicas (27% of traffic)

Resource Requirements:
  - RAM: 10 replicas × 200MB = 2GB
  - CPU: 10 replicas × 15% = 150% (1.5 cores)
  - Disk: ~500MB per replica = 5GB total
  - 8GB laptop: ✅ PLENTY OF HEADROOM

Real-World Equivalent:
  1,000 RPS × 10s think time = 10,000 concurrent users ✅
```

## 🏗️ **Architecture Design**

### **Service Scaling Configuration**

| Service | Min Replicas | Max Replicas (8GB) | Max Replicas (Production) | Target CPU | Target Memory |
|---------|--------------|-------------------|---------------------------|------------|---------------|
| **user-service** | 2 | 8 | 16 | 60% | 70% |
| **trip-service** | 2 | 10 | 20 | 60% | 70% |
| **driver-service** | 2 | 7 | 13 | 60% | 70% |
| **Total** | 6 | 25 | 49 | - | - |

**Resource Assumptions:**
- Per replica: 200MB RAM, 15% CPU (under load)
- 10 replicas × 200MB = 2GB RAM (easily fits in 8GB laptop)
- 25 replicas × 200MB = 5GB RAM (stress test limit for 8GB machine)
- Production: Scale horizontally with more nodes (not more replicas per node)

### **Scaling Triggers**

#### **Scale-Out Conditions (Add Replicas)**

1. **CPU Utilization >60%** (sustained for 15 seconds)
2. **Memory Utilization >70%** (sustained for 15 seconds)
3. **Response Time p95 >300ms** (indicates saturation)

**Scale-Out Action:**
- Add **2 replicas** per scaling event
- **1-minute cooldown** before next scale-out
- Cap at max replicas

#### **Scale-In Conditions (Remove Replicas)**

1. **CPU Utilization <30%** AND **Memory <35%** (sustained for 5 minutes)
2. **Response Time p95 <100ms** (indicates over-provisioning)

**Scale-In Action:**
- Remove **1 replica** per scaling event
- **5-minute cooldown** before next scale-in (avoid thrashing)
- Cap at min replicas

### **Auto-Scaling Algorithm**

```python
def evaluate_scaling(service, cpu, memory, current_replicas):
    config = CONFIG[service]
    
    # Scale-Out Logic
    if (cpu > config.target_cpu OR memory > config.target_memory) AND
       time_since_last_scale > scale_out_cooldown AND
       current_replicas < max_replicas:
        
        target_replicas = min(current_replicas + 2, max_replicas)
        scale_service(service, target_replicas)
        return
    
    # Scale-In Logic
    if (cpu < config.target_cpu * 0.5 AND memory < config.target_memory * 0.5) AND
       time_since_last_scale > scale_in_cooldown AND
       current_replicas > min_replicas:
        
        target_replicas = max(current_replicas - 1, min_replicas)
        scale_service(service, target_replicas)
        return
```

### **Capacity Extrapolation (CORRECTED)**

```
Key Insight: System capacity (RPS) ≠ User request rate
- System handles requests at maximum throughput
- Users spread requests over time (think time)

Current System Capacity (Story 2.2):
- 6 replicas handle 600 RPS max (50 VUs × 12 req/s/VU)
- With user think time (10s): Supports 600 × 10s = 6,000 concurrent users

For 10,000 Users:
- Required RPS: 10,000 / 10s = 1,000 RPS
- Current capacity: 600 RPS
- Scale factor: 1,000 / 600 = 1.67x
- Needed replicas: 6 × 1.67 = 10 replicas

Test Validation with 300 VUs:
- If 300 VUs sustain with p95 <500ms:
  - Capacity: 300 VUs × 12 req/s = 3,600 RPS max
  - Concurrent users: 3,600 RPS × 10s = 36,000 users supported
  - Proves 10k user capacity ✅

Docker Compose Limit (8GB RAM):
- 25 replicas = 5GB RAM
- Max RPS: 25/6 × 600 RPS = 2,500 RPS
- Max concurrent users: 2,500 × 10s = 25,000 users
- 10k user target: Easily achievable ✅
```
